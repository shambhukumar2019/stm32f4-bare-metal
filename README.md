# STM32F4 bare-metal blink firmware

This repository builds a bare-metal firmware image for an STM32F407VG (STM32F407VGTX) using CMake and the GNU Arm Embedded toolchain. The application configures the clock tree, sets the green LED on GPIOD pin 12 as an output, then toggles it forever with a busy-wait delay.

The board in use is an STM32F407VG-based Discovery-style board. The ST-LINK/V2.1 programmer appears as:

```text
Bus 001 Device 004: ID 0483:3752 STMicroelectronics ST-LINK/V2.1
```

## Firmware behavior

The entry point is `firmware/app/main.c`. It configures the STM32F407 PLL parameters for a 168 MHz system clock, enables the GPIOD peripheral clock, configures PD12 as an output, and repeatedly toggles that pin. The delay is a CPU busy-wait loop; there is no RTOS or scheduler.

The application uses direct peripheral-register access through the STM32 device and CMSIS headers. The repository also contains BSP, config, driver, and HAL CMake targets; these are currently project scaffolding rather than a full driver framework.

## CMake structure

The top-level `CMakeLists.txt` is deliberately small:

```cmake
cmake_minimum_required(VERSION 3.20)
project(blink LANGUAGES C ASM)

set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

include(${CMAKE_SOURCE_DIR}/config/stm32f407_target.cmake)
include(${CMAKE_SOURCE_DIR}/config/stm32f4_post_build.cmake)

add_subdirectory(firmware)
```

`config/arm-none-eabi.cmake` configures the cross-toolchain by locating:

- `arm-none-eabi-gcc`
- `arm-none-eabi-g++`
- `arm-none-eabi-objcopy`
- `arm-none-eabi-objdump`
- `arm-none-eabi-size`

The target settings in `config/stm32f407_target.cmake` add the Cortex-M4 flags to the MCU interface target:

```cmake
target_compile_options(stm32f407_mcu INTERFACE
    -Wall -Wextra
    -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard
    -ffunction-sections -fdata-sections
)

target_link_options(stm32f407_mcu INTERFACE
    -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard
    --specs=nano.specs
    -Wl,--print-memory-usage
    -Wl,-Map=${CMAKE_PROJECT_NAME}.map
    -Wl,--gc-sections
    -T${CMAKE_SOURCE_DIR}/firmware/vendor/platform/stm32f4xx/STM32F407VGTX.ld
)
```

The firmware target is created in `firmware/CMakeLists.txt` and linked against the MCU target and the project libraries:

```cmake
add_executable(${CMAKE_PROJECT_NAME}.elf
    ${CMAKE_CURRENT_SOURCE_DIR}/app/main.c
)

target_link_libraries(${CMAKE_PROJECT_NAME}.elf PUBLIC
    stm32f407_mcu
    config
    vendor
    hal
    drivers
    bsp
    app
)

add_fw_artifacts(${CMAKE_PROJECT_NAME})
```

`config/stm32f4_post_build.cmake` adds the post-link size output and creates the firmware image files:

```cmake
add_custom_command(TARGET ${TARGET_NAME}.elf POST_BUILD
    COMMAND ${CMAKE_SIZE} $<TARGET_FILE:${TARGET_NAME}.elf>
)

add_custom_command(TARGET ${TARGET_NAME}.elf POST_BUILD
    COMMAND ${CMAKE_OBJCOPY} -O binary $<TARGET_FILE:${TARGET_NAME}.elf> ${TARGET_NAME}.bin
    COMMAND ${CMAKE_OBJCOPY} -O ihex $<TARGET_FILE:${TARGET_NAME}.elf> ${TARGET_NAME}.hex
)
```

## Building with CMake

### Prerequisites

- CMake 3.21 or newer (for the version 3 presets in `CMakePresets.json`)
- Ninja
- GNU ARM embedded toolchain (`arm-none-eabi-*`)

Install the GNU Arm Embedded toolchain and ensure the `arm-none-eabi-*` tools are on `PATH`. If using the optional toolchain located under `tools/arm_gcc/`, add its `bin` directory:

```bash
export PATH="$PWD/tools/arm_gcc/bin:$PATH"
```

If the toolchain is installed system-wide, this may not be needed.

### Configure and build

The project defines `debug` and `release` presets in `CMakePresets.json`:

```bash
cmake --preset debug
cmake --build --preset debug
```

For a release build:

```bash
cmake --preset release
cmake --build --preset release
```

The generated outputs are placed in the build directory for the selected preset. For Debug:

```text
build/debug/firmware/blink.elf
build/debug/firmware/blink.bin
build/debug/firmware/blink.hex
build/debug/blink.map
```

The Release outputs are under `build/release/` with the same file names. The `.elf` is the linked executable; `.bin` and `.hex` are generated automatically after linking. No flashing is performed by the build.

To view the detailed compile and link commands while building:

```bash
cmake --build --preset debug --verbose
```

To build only the ELF target:

```bash
cmake --build --preset debug --target blink.elf
```

## Cleaning the build

Remove the generated object files while keeping the configuration:

```bash
cmake --build --preset debug --target clean
```

Remove the build tree entirely and reconfigure from scratch:

```bash
rm -rf build
cmake --preset debug
cmake --build --preset debug
```

## GitHub Actions

The workflow at `.github/workflows/ci.yml` runs on pushes to the `main` branch. It uses an Ubuntu GitHub-hosted runner, installs `gcc-arm-none-eabi`, then configures and builds the Debug preset with CMake. It does not currently run on pull requests, build the Release preset, run static analysis, upload firmware artifacts, or flash a board. The build outputs are available only in the runner unless the workflow is extended to upload them.

## Docker build environment

The Dockerfile uses Debian and installs CMake, Ninja, Cppcheck, and other utilities. It copies `tools/arm_gcc/` into the image and adds its `bin` directory to `PATH`; it does not install the ARM toolchain from the Debian package manager. Since `tools/` is Git-ignored, the toolchain must be present locally in the Docker build context to build the image.

Typical usage from the repo root:

```bash
docker build --progress=plain -f docker/Dockerfile -t blinker:v1 .
docker run --rm blinker:v1
```

The image configures the Debug preset during image build. Its default command builds that preconfigured source copy inside the container. To build the current checkout instead, mount the repository and override the default command so the mounted source is configured first:

```bash
docker run --rm -it \
  -v "$PWD:/blink" \
  -w /blink \
  --entrypoint /bin/bash \
  blinker:v1
```

Then, inside the container, run:

```bash
cmake --preset debug
cmake --build --preset debug
```

The build directory is mounted from the host, so the resulting firmware files remain in the checkout after the container exits. Docker Compose is not required for this single-container build.

## Programming the board

After the build succeeds, program the generated `.bin` or `.hex` image to the target using an ST-LINK-compatible tool such as:

- STM32CubeProgrammer
- OpenOCD
- `st-flash` (if installed)

The project currently produces `blink.bin` and `blink.hex`, which are intended to be flashed to the STM32F407VGTX flash memory via the ST-LINK programmer connected to the board.

## Notes

- The project is a bare-metal embedded firmware example; there is no RTOS or HAL driver framework layered above the direct register access.
- The linker script is `firmware/vendor/platform/stm32f4xx/STM32F407VGTX.ld`.
- The build intentionally uses the GNU ARM cross-compiler and generates raw binary and Intel HEX artifacts automatically after each link.
